SNES terms (plain language)
---------------------------
- Field / frame: one screen refresh, 1/60 s (NTSC SNES: 60.0988 Hz).
- PPU: the SNES picture chip. Draws up to 4 background layers (BG1-BG4) plus sprites (OBJ).
- BG mode: which layer combination is in use (modes 0-7). Mode 7 = one rotating/scaling layer.
- Scroll (HOFS/VOFS): each layer's own camera offset. Lagoon's code calls them hScroll[]/vScroll[].
- OAM: the sprite list (128 entries on SNES vs 64 on NES), same idea as on the NES.
- HDMA: the SNES changing a register on every line automatically (gradients, wavy water,
  split scrolling). The NES equivalent was our "scroll bands" done by hand.
- Colour math: blending layers together (transparency, shadows, fades).
- INIDISP: master screen brightness 0-15 (fades). 15 = full.
- WRAM: the game's work memory (like NES RAM, 128 KiB). Addresses below are WRAM.

Where things are (answers to the Step 1 questions)
---------------------------------------------------
1. The frame loop: the engine owns it, not Lagoon.
   snesrecomp/runner/src/desktop/host_main.c (5,854 lines after the patch), main loop ~line 4850:
   RtlRunFrame (emulate one field) -> CaptureSimulationFrame -> DrawPpuFrameWithPerf (present).
   src/main.c is a thin "shim" that fills a hook table (SnesDesktopHostGame) and calls
   snesrecomp_desktop_main(). One thread: no emulation thread / second core.

2. How the picture is made:
   - The engine's PPU draws the original 256x224 picture ("field").
   - Lagoon then REDRAWS the world itself on the CPU for widescreen/zoom: lagoon_widescreen.c +
     lagoon_scene_renderer.c ("title compositor"). It rebuilds the room's terrain from copied tile
     data at any camera position, draws supported actors (lagoon_wide_entities.c), HUD on top.
   - It only replaces the original picture after a whole-field exact comparison (their self-check,
     "full-word, whole-field equality"), and draws only from data copied at frame end ("TryPresent
     never reads the mutable guest"). These are our self-check and snapshot rules, already built in.
   - Anything not qualified (menus, spells, cutscenes, fades, unsupported scenes) shows the original.
   - Zoom/expanded view is composed on the CPU per presented picture (presentation_compose hook).
     Final scaling and Enhanced pixels (EPX/MMPX) run on the GPU. Linux = OpenGL presenter.
     Windows = D3D11 (not our concern on CachyOS, but our code must not break it).

3. Hooks between "frame done" and "picture shown" (our HOST_EXTRAS equivalent) - all exist:
   before_run_frame / after_run_frame   around the emulated field
   begin_sim_frame / end_sim_frame      around drawing the PPU picture (end gets the 256-wide field)
   draw_frame(dst, field, w, h, alpha)  compose the picture to show  <- Lagoon: LagoonHost_DrawFrame
   presentation_compose                 the zoomed/expanded composition per picture
   on_reset                             timeline jumped (reset, state load, overlay closed)
   presentation_hz(display_refresh)     <- NOT USED BY LAGOON. See point 4.

4. Frame pacing: THE BIG FIND.
   The engine already supports in-between pictures (it came from Super Metroid's port):
   - If the game sets the presentation_hz hook, the clock (host_clock.c) presents at that rate
     while simulating at 60.0988, and calls draw_frame again for every picture with
     alpha = 0..1 = how far we are between the last two simulated fields.
   - In that mode the driver's VSync is switched off automatically (the engine paces itself).
   - In-between pictures only happen while waiting for the next field (single thread), like our
     engine before the emulation thread. Second core = later, only if the pacing numbers ask.
   - Lagoon's draw path ignores alpha today ((void)alpha in LagoonWide_DrawFrame).
   So Step 4.1 is mostly: set presentation_hz from our setting, and make Lagoon's drawing use
   a position for the in-between moment. No engine change needed for the basic version.

5. "Only 30 FPS": answered by their own test, to be confirmed by measuring.
   tests/lagoon_cloud_motion76_test.c: "Half-rate main tick reproduces the measured one
   tick/two fields". Lagoon's main game logic runs once every TWO fields (30 Hz): case (a) in
   lagoonplaybook section 0.5, the best case for in-between pictures (30 -> 240 = 8 pictures
   per game step). The window still runs at 60, showing each game picture twice.
   Important consequence: the engine's alpha is measured between FIELDS (60 Hz). For a 30 Hz
   game we need our own phase: which field of the pair we are in, and blend over the pair
   (same as the 30 Hz handling on Double Dragon II). Confirm in Step 3 that camera AND sprites
   step on the same field of the pair, and whether the "faster walking" QoL option changes it.

6. Camera: WRAM $0480/$0482 = BG1 (main terrain) X/Y, $0484/$0486 = BG2 X/Y, $048E = room number
   (0..$4A, 75 rooms). Parallax rooms move BG2 at its own rate (quarter scroll); the renderer
   already handles both layers separately. Top-down game: expect X and Y moving together.
   Existing camera features: QoL "centered camera" (lagoon_qol.c), live zoom 1x/1.25x/1.5x
   (R3 / Ctrl+Z), widescreen aspects, square pixels. Smooth camera must sit inside their renderer's
   camera (view_origin() in lagoon_scene_renderer.c), not on top of it.

7. Measuring tools already there (no need to build ours first):
   SNESRECOMP_PRESENT_LOG=file.csv   every presented picture: present, frame, alpha, crc32, luma
                                     (tools/present_curve.py summarises it)  ~ our pacing log
   SNESRECOMP_HOST_PROFILE=1         wall time split: guest, raster, compose, present, wait ...
                                     ~ our CYC_PACING_LOG / MM2_PERF_LOG
   SNESRECOMP_OSD_FPS=1              FPS readout on screen
   SNESRECOMP_SCREENSHOT_FROM/_TO/_DIR  pictures by frame number
   --script <file>                   scripted input (tools/script_*.txt examples) ~ our route.txt
   --campaign-warps <plan>           private test cheat: start in any of the 75 rooms
                                     (tools/CAMPAIGN-WARPS.md, campaign_rooms.py)
   --framedump, tools/framedump_summary.py, tools/ram_track.py, Mesen lua scripts (tools/*.lua)
   Save states: F7 menu (engine's), rewind filmstrip.
   Missing compared to our NES logs: a per-frame scroll/OAM/palette log. Step 2 adds a small one
   (game-side, in after_run_frame / end_sim_frame), reading only what the frame finished with.

Building on Linux (from docs/BUILDING.md, scripts/build_port.py)
----------------------------------------------------------------
Needs Python 3.11+, Rust (cargo), CMake 3.20+, Ninja, C/C++ compiler, SDL3 (static, fetched by the
build), zlib, OpenGL/X11/Wayland/audio dev headers.
  python3 -P scripts/build_port.py --rom ~/Projects/LagoonSNESRecomp/lagoon.sfc
-> applies the engine patch, generates the game's C from the ROM (src/gen/, never committed),
   builds the strict-native game in build-port/. Program: build-port/LagoonSNESRecomp.
Note: the patch step modifies the snesrecomp submodule's files (expected; it shows as "modified
content" in git status). Don't commit that submodule change.

Step 4.1 (2026-11-18): in-between pictures, first version
---------------------------------------------------------
src/lagoon_smooth.c/.h (ours). Setting: config.ini [Lagoon] PicturesPerSecond = 60|120|180|240
(60 = off, default). LAGOON_PICTURES=n overrides one run. LAGOON_SMOOTH_LOG=file: per picture
"frame alpha t drawn reason"; exit line [lagoon-smooth] with counters (stderr / profile.txt).
How: presentation_hz hook -> host presents at that rate and calls draw_frame with alpha. After
their scene renderer replaced the picture with its verified packet (TryPresent), we redraw that
same packet with camera + sprites part way between the last two game steps:
  t = (fields since step + alpha) / period (period = fields between steps, normally 2).
  Interpolated in world coords, rounded identically for camera and sprites (static things stay on
  the ground, Nasir stays fixed on screen). Steps > 8 px = jump, no in-between.
  Whole pixels at game resolution (crisp; MMPX still works). 180 = even rhythm for 3 px steps
  (0.5 px a picture); 240 = 3 px over 8 pictures (uneven 0/1 pattern). Sub-pixel = later option.
Their files: lagoon_scene_renderer.c/.h (+Motion accessor, +RenderMotion, s_motion_render flag:
  no background cache, backgrounds from the room map instead of the streamed VRAM tilemap),
  lagoon_widescreen.c (call after TryPresent, zoom 1x only), main.c (presentation_hz, reset, config).
Self-checks: only over a verified packet (TryPresent replaced); every new packet the room-map
  redraw at the real positions must equal that picture, else no in-between pictures.
Limits: widescreen on, zoom 1x; scenes their renderer doesn't qualify (menus, spells, cutscenes,
  fades) stay at 30 Hz motion. Delay: up to 2 fields (33 ms) more than the original.
Offline test (stub renderer, camera following Nasir, static + walking enemy, 240): PASS.
build-port/config.ini set: Widescreen 1, Fullscreen 1, [Lagoon] WideAspect 16:9, ViewExtent 1,
  PicturesPerSecond 180 (old file kept as config.before-smooth.ini).
